## 1) Dual-insulin regimen (the clinical fix)
Problem: the app allowed only ONE insulin type per patient — wrong for standard MDI therapy where children use a long-acting (basal) + rapid-acting (bolus) insulin.
- **DB (applied live + repo migration):** `patients.basal_insulin`, `patients.bolus_insulin`; `insulin_regimens.regimen_type` ('mdi'|'pump'|'premix'), `basal_insulin`, `basal_dose`, `bolus_insulin`.
- **AddPatient:** two dropdowns — Long-acting (basal): glargine U100/U300, detemir, degludec, NPH; Rapid-acting (bolus): aspart, lispro, glulisine, faster aspart, regular human, premix 70/30; each with 'None'; basal dose field; bilingual hint.
- **Regimen settings:** regimen-type chips + dual dropdowns + basal dose; new rows always require fresh clinician approval (fail-closed kept).
- **Displays:** home cards, dashboard header, clinician list/detail now show "Glargine + Aspart" style; log screen regimen info updated.
- Insulin lists sourced from ISPAD consensus guidance (see `.cluster/ux-round6/subagent_11.md`).

## 2) Login/auth hardening (per "alisha" playbook audit — `.cluster/ux-round6/subagent_13.md`)
- Tri-state Google sign-in: `signed-in` / `cancelled` (silent) / `unavailable` (bilingual alert) — no more silent dead-ends.
- Sign-out: check result + `scope:'local'` fallback so the stored session is always removed.
- Duplicate-email sign-up: "Account already exists → Log in" (handles both error and anti-enumeration fake-success).
- Inline password rule before submit; friendlier mapped errors (email-not-confirmed, rate limit); bottom clearance ≥48dp (§13); implicit OAuth flow pinned explicitly.
- Guest cleanup/upgrade plan documented in code (implementation later).
